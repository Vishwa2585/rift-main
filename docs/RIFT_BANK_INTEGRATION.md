## 1. Overview & Architecture

Project RIFT provides an authoritative real-time cross-chain bridge exploit detection and transaction security layer for **RIFT Bank**. Before high-value or cross-chain bridge transactions are submitted or settled, RIFT Bank interfaces with RIFT to perform deterministic preflight policy checks, manage two-party sender/receiver approvals, bound transactions cryptographically to hardware security keys (RIFT KEY), ingest live bridge events, and monitor settlement finality.

```
+------------------+         REST / HMAC Webhooks         +--------------------+
|                  | -----------------------------------> |                    |
|    RIFT Bank     |   POST /transactions/intent          |     RIFT Core      |
|  (Core Banking)  |   POST /transactions/:id/approval    | (Detection Engine) |
|                  |   POST /webhooks/bank                |                    |
+------------------+ <----------------------------------- +--------------------+
                                Authoritative Status
                             & Cryptographic Challenges
```

## 2. Authentication & Security

### 2.1 Server-to-Server API Key
All bank integration endpoints (except `/api/v1/health` and `/api/v1/webhooks/bank`) require a server-to-server API key passed via the HTTP header:

```http
x-rift-api-key: <RIFT_API_KEY>
```
*Requests without this header or with an invalid key receive `401 Unauthorized` with `{ "error": "Unauthorized: invalid or missing x-rift-api-key" }`.*

### 2.2 Webhook HMAC-SHA256 Signature
Bridge and settlement event webhooks sent from RIFT Bank to RIFT (`POST /api/v1/webhooks/bank`) are signed using HMAC-SHA256 with the shared secret `RIFT_WEBHOOK_SECRET`. The hex digest must be transmitted in the header:

```http
x-rift-signature: <hex_hmac_sha256_digest>
```
RIFT computes `crypto.createHmac("sha256", secret).update(rawPayload).digest("hex")` and validates the signature using timing-safe comparison. Invalid signatures are rejected with `403 Forbidden`.

### 2.3 Privilege Separation & Nonce Hardening
- Privileged keys are never exposed to browser or mobile frontends.
- RIFT transaction challenges (`/api/v1/transactions/:id/challenge`) require a transaction-bound digest and an atomic, single-use nonce (`Rule R-08`). Replayed nonces are permanently rejected with `409 Conflict`.

## 3. Transaction Identifiers & Counterparty Model

RIFT maintains a strict distinction between blockchain transaction hashes and internal financial identifiers:

| Identifier | Format | Description |
| :--- | :--- | :--- |
| **RIFT Transaction ID** | `RFT-TX-xxxx` | Authoritative internal transaction identifier across all chains. |
| **Bank Operation ID** | `BNK-OP-xxxx` | RIFT Bank's internal payment order / transfer reference. |
| **Correlation ID** | `CORR-<timestamp>` | Links source chain deposit with destination chain withdrawal. |
| **Bridge Message ID** | `MSG-xxxx` | Unique message payload ID generated by the cross-chain bridge. |
| **Counterparty ID** | `CPT-<addr>` | Unregistered counterparty reference (no mandatory RIFT account). |
| **Claim Token** | `CLM-<hash>` | Escrow claim token for unregistered beneficiaries. |
| **Blockchain Hashes** | `0x<64_hex_chars>` | Real transaction hashes on source and destination networks. |

Recipients do **not** need a pre-existing RIFT account to be referenced in transactions. Addresses not mapped to registered client IDs are assigned `recipientType: "UNREGISTERED_WALLET"` with a stable counterparty reference `CPT-<truncated_hash>` or `recipientType: "PENDING_CLAIM"`.

### 4.4 Record Two-Party Consent Decision
**Endpoint:** `POST /api/v1/transactions/:id/approval`  
**Headers:** `x-rift-api-key: <RIFT_API_KEY>`  
**Request Body Schema:**
```json
{
  "party": "sender",
  "decision": "APPROVED",
  "reason": "Client confirmed via banking portal MFA"
}
```
*Allowed `party`: `"sender"` | `"receiver"`.*  
*Allowed `decision`: `"APPROVED"` | `"REJECTED"`.*

**Behavior & Policy Re-evaluation:**
- **Rejection:** If either party rejects, the transaction transitions to `state: "REJECTED"`, `status: "rejected"`, `settlementHeld: true`.
- **Approval:** When both sender and receiver have approved, the transaction transitions to `state: "READY_FOR_EXECUTION"`, `status: "authorized"`.
- **Timeout Enforcement:** If the current timestamp exceeds `twoPartyApproval.deadlineTimestamp`, RIFT rejects the approval with `410 Gone` (`Approval window expired. Transaction held.`) and updates state to `EXPIRED`.

---

### 4.5 Execute Hardware Key Cryptographic Challenge
**Endpoint:** `POST /api/v1/transactions/:id/challenge`  
**Headers:** `x-rift-api-key: <RIFT_API_KEY>`  
**Request Body Schema:**
```json
{
  "nonce": "NONCE-847291",
  "digest": "0x8fa3...b02c"
}
```

**Verification Logic:**
1. **Nonce Replay Check:** Checks if `nonce` has already been recorded in the persistent single-use store. Replays immediately return `409 Conflict` (`Cryptographic nonce already consumed (replay attack detected)`).
2. **Digest Integrity Check:** Recomputes `computeTransactionDigest` across canonical fields (`txId`, `sourceChain`, `destChain`, `amount`, `asset`, `recipient`, `nonce`, `expiresAt`). Tampered amounts or recipients return `400 Bad Request` (`Invalid cryptographic challenge digest`).
3. **Atomic Consumption:** Atomically records `nonce` as consumed and sets `nfcVerified: true`, unlocking sovereign execution.

## 5. Transaction Lifecycle & State Transitions

The RIFT state machine strictly enforces deterministic progression. Distributed execution stages are separated from local database records to prevent split-brain anomalies:

```
[Intent Submitted]
        |
        v
    [CREATED]
        |
        v
[PENDING_RISK_ASSESSMENT]
        |
   +----+--------------------------+
   |                               |
   v                               v
[PENDING_PARTY_APPROVAL]   [PENDING_RIFT_KEY]
(Two-party consent >= $5M) (Sovereign >= $100M)
   |                               |
   +----+--------------------------+
        |
        +---> [REJECTED] / [EXPIRED] (If timeout or rejected)
        |
        v (All criteria satisfied)
[READY_FOR_EXECUTION]
        |
        v
   [SUBMITTED]
        |
        v
   [CONFIRMED]
        |
        v
    [SETTLED]
```

### Supported State Definitions:

1. **`CREATED`**: Intent received and validated; assigned stable `RFT-TX-xxxx` identifier.
2. **`PENDING_RISK_ASSESSMENT`**: Automated rules R-01 through R-09 currently evaluating route, token mapping, and volume.
3. **`PENDING_PARTY_APPROVAL`**: Mutual consent required from sender and receiver.
4. **`PENDING_RIFT_KEY`**: Hardware NFC challenge pending single-use cryptographic tap.
5. **`READY_FOR_EXECUTION`**: All security pre-conditions met; RIFT Bank authorized to broadcast on-chain transaction.
6. **`SUBMITTED`**: Transaction broadcast to source network; initial transaction hash generated.
7. **`CONFIRMED`**: Source confirmations meet finality window requirement (e.g. 32 blocks on Ethereum).
8. **`SETTLED`**: Destination execution verified, correlated, and reconciled.
9. **`HELD`**: Suspicious anomaly detected; automated hold placed on settlement execution.
10. **`REJECTED`**: Explicit rejection by sender, receiver, or security officer.
11. **`EXPIRED`**: Approval deadline elapsed without mutual consent; backend rejects execution.
12. **`FAILED`**: Blockchain execution reverted on-chain.
13. **`RECONCILIATION_REQUIRED`**: Discrepancy observed between database commit and on-chain log index.

## 6. Detection Rules Mapping (CSB-01)

RIFT evaluates every transaction intent and correlated bridge pair against the official CSB-01 detection rules:

| Rule ID | Rule Name | Trigger Criteria | Severity | Action |
| :--- | :--- | :--- | :--- | :--- |
| **R-01** | Unmatched Destination Event | Credit observed on destination without prior verified source deposit | **CRITICAL** | Immediate Hold & Alert |
| **R-02** | Cross-Chain Amount Mismatch | Discrepancy between source debit and destination credit | **HIGH** | Hold & Investigator Incident |
| **R-03** | Finality Window Violation | Destination minted before source reached required confirmations | **HIGH** | Mark Flagged |
| **R-04** | Identifier Reuse / Replay | Duplicate bridge message ID used across multiple transactions | **CRITICAL** | Reject & Blacklist |
| **R-05** | Token Mapping Anomaly | Destination mints an unmapped or unapproved token pair | **MEDIUM** | Risk Score +45 |
| **R-06** | Unauthorized Beneficiary | Destination recipient address differs from initiator intent | **HIGH** | Hold & Escalate |
| **R-07** | Velocity / Volume Spike | Transaction amount exceeds rolling pool volume threshold | **MEDIUM** | Party Approval Mandate |
| **R-08** | RIFT KEY Replay Protection | Cryptographic challenge nonce already consumed or digest altered | **HIGH** | Reject Challenge |
| **R-09** | Synthetic Data Provenance | Data tagged as synthetic or replay simulation | **INFO** | Watermark as SIMULATED |
